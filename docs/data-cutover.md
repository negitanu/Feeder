# Web データの移行・切替・復旧

これは計画であり手順の実証結果ではない。旧ローカル版と同期のデータは対象外。既存 Web の記事・既読・スター・履歴・順序・設定・API キー・調査・根拠・ジョブ・予算・blob 等は、現行の意味と参照関係を棚卸しして保全する。秘密値は記録や fixture へ出力しない。

1. 元システムの schema version、各種データ・ファイル・保管パス、アプリ版、API と実際の運用条件を確認する。schema 19 は参照したソースの値であり、稼働環境の確認結果ではない。
2. 旧アプリの書込みを停止した一貫した時点で、SQLite のバックアップ API 等により WAL を含む整合 DB と対応する根拠 blob、必要な設定を取得する。取得方法は現行の復旧手順と突き合わせる。秘密は安全に保持し Git へ入れない。
3. 別環境で復元し integrity_check、foreign_key_check、blob のハッシュ・サイズ、参照整合性を確認する。合成データで差分試験を繰り返す。直接互換と変換移行のいずれを採用するかはこれらの結果を根拠に決定する。
4. 切替直前にすべての旧 writer（web、worker、observer 等）を止め、最終バックアップ・復元確認・移行を実施する。記事・状態・順序・調査関係・設定・ジョブ・添付を対象別に照合し、結果を記録する。同一 DB に旧新を同時書込みさせない。
5. Feeder を起動し health、実 HTTP、認証、収集、代表 UI を確認する。外部 Access／有料 API／通知は模擬検証と実環境検証を区別する。
6. 復旧判断の責任者・条件を決め、Feeder を停止して旧版と対応バックアップを復元する。切替後に Feeder へ書き込まれたデータの退避と再適用／損失範囲を事前に決定・検証し、単純な旧バックアップ復元による無自覚なデータ損失を防ぐ。

旧データ、バックアップ、旧環境は経過時間だけを理由に削除しない。切替の実施条件、実所要時間、リカバリ目標はリハーサル後に決定する。
