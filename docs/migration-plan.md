# 段階的移行計画

## 目的と前提

FeedAstrolabe Web の機能と利用者データを Feeder に移す。Rust、React/TypeScript、SQLite を基本候補とし、認証や renderer 隔離を含む既存運用を維持する。デスクトップアプリ、同期、デスクトップデータの移行は終了する。実行中の Web とその実データはそのまま維持する。Web の既存データ移行は必要。

設計上の段階であり、いずれも完了を表さない。個々の着手前に OpenSpec で対象・受入条件・設計を具体化し、必要な本仕様を作る。旧仕様のスナップショットは参考資料であり、自動的に全て Feeder の仕様にならない。

## 0. 基準線と技術検証

- 現行 Web の README、本仕様、コード、API、既存テストと運用文書を照合し、[機能対応表](source-inventory.md)をシナリオ単位に詳細化。未コミット同期差分と既存実装を区別する。
- schema version 19 はソース上の値であり、実稼働 DB バージョン・データ量・blob の状態は未確認。アクセス権とバックアップ手順を設計する。
- Rust API・SQLite・React・ジョブ・renderer の候補を評価。最新安定依存、ライセンス、OS/コンテナ互換性、脆弱性、ビルドと必要な固定方法を確認し、選定理由を記録する。レンダラーに Python が当面残る場合は明示する。
- 完了条件: 機能・API・データ・運用の追跡表、未決事項、技術選定と検証計画をレビュー可能な状態にする。

## 1. 最小の縦切り

- Rust API、React 画面、SQLite を用意し、記事一覧・詳細・既読・スターを通す。合成データと旧 DB の生成 fixture を使用する。
- 縦スクロール追加、一覧位置、詳細の既読と履歴、テーマ、PC／モバイル、キーボードを旧仕様で確認する。
- DB を直接互換とするか、明示的な変換とするかを比較。実データを使う場合は利用者が保管する整合コピーで明示的に検証し、外部へ持ち出さない。
- 完了条件: 一連の表示・更新・再起動が成功し、旧版とデータ内容を照合でき、テスト／OpenSpec strict／差分が通る。

## 2. 読書と収集の基盤

- RSS/Atom 発見・プレビュー・購読、フォルダーとフィードの操作・順序・停止再開、条件全体の「全て既読」、検索、OPML、画面設定と API 認証を移す。
- Web/worker の排他、失敗時の保持、安全な外部取得と定期処理を移す。
- 完了条件: 旧仕様のシナリオと API 契約、並行処理、画面遷移・保存・復帰、セキュリティの回帰を通す。

## 3. 調査・根拠・運用

- 案件・メモ版管理・タグ・根拠・添付・引用、レポート・通知・バックアップ・復元、ワーカー運用を移す。
- 完了条件: 参照関係、公開区分、添付ハッシュとファイル、復旧・競合制御を合成 fixture と復元試験で確認する。

## 4. 外部連携と高度な分析

- Mastodon/Bluesky、OpenRouter/OrcaRouter、Ollama、watchlist、対象・関係、セキュリティ／ネットワーク／AI 研究、ページ観測を段階ごとの変更として移す。
- observer と隔離 renderer のネットワーク分離・broker・上限を維持し、利用者認証や秘密情報の保持・予算・ジョブの送信境界を検証する。X の新規収集は再導入せず保存済み記事を保持する。
- 完了条件: 模擬 API を用いた各契約と障害回復を通し、有料 API・実サービス・外部 Access の未実施検証を個別に明記する。

## 5. 全体受入と切替

- 全機能の仕様と追跡表に結果を記録し、従来 API・バックアップ・設定形式の互換性と例外を確定する。コンテナの非 root、read-only、cap drop、renderer 隔離、secret の扱いと health を検証する。
- [データ移行・切替](data-cutover.md)の整合バックアップ、復元、書込み停止、移行、照合、復旧リハーサルがゲート。既存 DB/blob に直接変更する前にバックアップを検証する。
- PC／モバイル、ライト／ダーク／システム、マウス・タッチ・キーボード、戻り先と履歴を確認する。OpenSpec strict、依存監査、差分と秘密情報を確認する。
- 本番反映時はコンテナを再構築・再起動し、health と実 HTTP、必要な実 Access を確認。承認前提や未検証事項は実際の環境と結果に基づき記録する。

## 依存関係

0 → 1 → 2 → 3・4 → 5。3 と 4 の内部は依存関係を決めて分割できるが、全受入の前に現行 Web を停止・削除しない。移行期間の二重書込みは許可しない。
