# 情報収集の動向と Feeder の拡張候補

確認日: 2026-11-07 JST。コード基準: `4ad4b4b`。

この文書は一次資料と現行実装に基づく提案であり、確定した実装計画・実装済み機能ではない。優先順位は Feeder への適合性から判断したもの。市場シェアや利用者全体の傾向を測定したものではない。公開日・更新日が分かる資料は日付を明記し、古くからある方式を新発明として扱わない。

## 推奨する方向

収集の確実性を整え、その上で「同じ話題を一度で把握する」「読んだ後の訂正に気づく」「関心のある新着を絞る」体験を強める。最初の実装単位は **SNSの継続取得と待機制御 → 同じ話題の集約 → 記事の更新差分** を推奨する。

Web専用のRSS／SNS Readerという方針を維持する。研究ワークスペース、関係グラフ、調査エージェント、専用rendererによるページ観測を追加する提案ではない。記事の改訂履歴は、通常のフィード再取得で受け取った内容に限定する。

## 一次資料で確認した動向

- **読者が調整できる選別。** NewsBlurは2026-11-05、タイトル・著者・タグ・本文・URLに対する分類ルールを直接入力し、適用範囲と優先／抑制／非表示を選ぶUIを発表した。Feederのミュートを、適用例が分かる読書設定へ発展させる参考になる。[NewsBlur公式](https://blog.newsblur.com/2026/11/05/type-a-classifier-into-the-trainer/)
- **公開後の更新も読む。** Inoreaderは2026-10-19、取得した記事のタイトル・本文の改訂を保存して差分表示する機能を発表した。Reader内の「新着」の価値は新規記事だけに限られない。[Inoreader公式](https://www.inoreader.com/blog/2026/10/introducing-article-edit-history.html)
- **単語から対象・話題へ。** Inoreaderは2026-09-14、企業や製品等の識別、検索、継続的なトピック購読を強化した。ただし公式説明でも言語・対象フィードの制限がある。Feederでは最初から汎用の実体識別を目指さず、利用者が確認できる別名辞書と検索条件を候補にする。[Inoreader公式](https://www.inoreader.com/blog/2026/09/introducing-mentions-redesigned-search-and-smarter-monitoring-feeds.html)
- **メールも読む場所へ集める。** Inoreaderは2026-08-14の紹介で、専用アドレスへ届くニュースレターを記事として扱う導線を示している。機能そのものの初回公開日とは断定しない。[Inoreader公式](https://www.inoreader.com/blog/2026/08/a-better-way-to-keep-up-with-newsletters.html)
- **URLを超えた重複抑制。** Feedlyの自動ニュースレター仕様は2026-03-19更新で、本文の重なりや近い時期の同一ニュースを重複の判断材料にしている。通常Readerと自動ニュースレターの判定は同一とは限らず、他社の閾値をそのまま採用しない。[Feedly公式](https://docs.feedly.com/article/847-article-deduplication-automated-newsletters)
- **AIの提供元と鍵を選べる構成。** Inoreaderは2026-04-14に提供元の選択と、対象プランでの持ち込みAPIキー・モデル選択を発表した。Feederでは既存の `.env` 方針と相性がよい。[Inoreader公式](https://www.inoreader.com/blog/2026/04/choose-your-ai-platform-for-intelligence-features.html)

これらからの推論は、収集対象の増加と並行して、重複・選別・更新・読む負担の改善が製品上の重点になっている、というもの。各社の発表だけから効果や普及率までは判断できない。

## 最新情報を取り込む方法

**基本経路:** 発行元のRSS／Atom・公式更新履歴を優先し、公開SNSは公式APIで補完する。HTTPの条件付き取得は既にFeederにあるため再実装せず、欠けている継続取得と待機制御を補う。条件付きGETとRetry-Afterは既存のHTTP標準である。[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)、[429の定義・Retry-After](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)

**鮮度が必要な購読の候補:** WebSubは対応する発行元・hubから更新を受け取る仕組み。2018年以前からの方式で、現在のW3C勧告は2026-06-02版。Blueskyの現行Jetstream資料には、購読DID等による絞り込み、カーソルでの再開と重複配信への対応がある。どちらも全収集の置換ではなく、対応ソースへの追加経路として評価する。[W3C WebSub](https://www.w3.org/TR/websub/)、[Bluesky Jetstream](https://bsky.network/ja/docs/jetstream/)

**RSSのない情報源:** 他社ではページからフィードを作る機能がある。[Inoreader Web feeds・2026-10-30更新](https://www.inoreader.com/help/pro/web-feeds/how-do-i-create-a-web-feed)。Feederは外部アダプターが生成したRSSを受け取る方向が現在の構成に合う。RSSHub公式は各種ソースのルートとRSS発見用Radarを提供している。[RSSHub公式](https://github.com/DIYgod/RSSHub)。RSSHubの配備文書は今回403で取得できず、個別ルートの動作・必要認証は未検証。

**外部の話題性:** Google Trends公式APIの現行案内は限定alphaの申請制。利用可能と仮定して基幹機能にしない。検索関心は記事の正確さや重要性を表す指標でもない。[Google公式案内](https://developers.google.com/search/apis/trends)、[2025-07-24発表](https://developers.google.com/search/blog/2025/07/trends-api)

## 実装候補8件

### 1. 取りこぼしが分かる収集 — 優先1・規模: 中

現状: 条件付きGET・304・取得リース・診断は実装済み。SNSは1回40件で継続ページングがない。429専用待機・指数バックオフも未実装。[収集処理](../backend/src/collection.rs)、[SNS取得](../backend/src/social.rs)、[検証上の制約](verification-reader-expansion.md)

提案: ソースごとの継続位置と次回可能時刻を保存し、ページ数・時間の予算内で追いつく。429／503のRetry-After、失敗時バックオフ、同一ホストの同時接続制限を追加する。収集診断に「最新まで取得」「続きあり」「再試行待ち」「欠落の可能性」を表示する。APIが過去分を返さない場合は完全性を保証しない。

受入案: 40件超の新着、途中切断、再起動、429、古いリースの応答を合成データで検証。既読・スターを保ち、同じ投稿を再受信しても増殖しない。実SNSの接続受入を別に記録する。

後段: 需要があるソースだけWebSub／Jetstreamを検討。WebSub callbackを設ける場合、Cloudflare Accessでhubが到達できる経路を設計し、その専用経路で購読検証・署名確認・再送制御を行う。Reader全体の認証は維持する。

### 2. 同じ話題をまとめて読む — 優先1・規模: 中〜大

現状: 最新1,000件を正規化URLでまとめる。内容類似の判定はない。[重複表示](../backend/src/duplicates.rs)

提案: 完全一致の重複と「関連する同じ話題」を別に扱う。本文の指紋、タイトル、近い発行時刻を候補抽出に使い、最初は機械学習API不要で実装する。記事行に「関連3件」のように表示し、展開で各記事へ移動する。原本と各記事の状態を残し、グループの解除・誤判定修正を可能にする。索引を用意して最新1,000件制限を解消する。

受入案: 日本語／英語、転載、同じ製品の別リリース、続報、短文を含む合成fixtureで誤った集約を評価。既読の連動を既定にせず、元記事を失わない。

### 3. 読んだ後の訂正・追記 — 優先1・規模: 中

現状: 同じ購読・外部IDの記事は再取得時にタイトル・本文等を上書きし、過去版は残らない。[保存処理](../backend/src/collection.rs)

提案: 通常のRSS／SNS再取得で変化を検出したら版を保存し、「更新あり」と差分を表示する。発行日時・提供元の更新日時・Feederの検知日時を分ける。既読は勝手に戻さない。配信元から変更後本文を受け取れない記事は検知できないことを示す。

受入案: 内容不変の再取得で版を増やさない。日時表記だけの揺れと本文の変更を区別し、既読・スター・あとで読むを維持する。版を含むバックアップ／復元と保存容量の上限を先に設計する。

### 4. トピック購読と説明できる話題表示 — 優先2・規模: 中〜大

現状: 保存検索、DB共有検索、キーワードミュートがある。共有検索の名称・条件編集UIは未実装。[共有検索](../backend/src/smart_folders.rs)、[ミュート](../backend/src/mute_rules.rs)

提案: 保存検索に別名・除外語・対象フィード／フォルダーを設定し、保存前に該当記事をプレビューする。「優先」「通常」「ミュート」の効果を説明できるようにする。トピックに新着数と発行元数を表示し、対応する記事へすぐ戻れるようにする。UIは通常の記事一覧と設定に統合する。

話題表示の案: 「購読内で増えている話題」と明記する。直近6時間の重複除外記事数と、過去7日の同じ時間帯の基準値を比較する。開始直後はデータ不足とし、倍率だけで並べず最低件数・発行元数を併記する。取り込み直後の過去記事や障害復旧時の大量取得を急増扱いにしない。発行元の数は独立した事実確認の数を意味しない。

受入案: 別名の誤一致、ミュート優先、対象購読の削除、タイムゾーン、初回取り込み、収集障害で結果が誤解を招かないこと。これは外部Web全体の検索インデックスではない。

### 5. ニュースレターを通常の記事へ — 優先2・規模: 中〜大

現状: メール受信・ニュースレター専用取込は未実装。RSSを公開しているニュースレターなら既存購読で扱える。

提案: 最初は専用メールボックスの指定フォルダーから取得する方式を検討する。購読単位・Message-ID等で重複を防ぎ、送信元・件名・配信日時を通常の記事に対応させる。個人メールボックス全体へのアクセスを前提にしない。接続先・資格情報は `.env` で管理する。受信サービスが必要な専用アドレス発行は別段階にする。

受入案: 合成MIMEで日本語、HTML／テキスト、同一メールの再取得を確認。危険なHTML・追跡画像を処理し、解約リンクを自動訪問しない。メール由来の内容は外部AIへ既定で送信しない。

### 6. 情報源を追加しやすくする — 優先2・規模: 中

現状: サイトからRSS／Atomを発見・プレビューして購読できる。RSSHub専用の発見・設定UIはない。ただしRSSHubが通常のRSSを返せば既存Readerで購読できる。[発見処理](../backend/src/discovery.rs)

提案: URLを貼ると、公式フィード候補、対応SNS、設定済み外部アダプターの候補を並べる。GitHub Releases、YouTube、公開コミュニティ等も、公式の配信手段を確認できたものからテンプレート化する。生成フィードは提供経路と最終成功を表示し、壊れたルートに気づけるようにする。

受入案: 候補の実プレビューと重複購読の抑止。内部アダプターを追加する場合はその接続先だけを明示許可し、任意の内部IPへ取得できるようにSSRF制限を緩めない。追加サービスの設定も既存の単一Compose／`.env`方針に合わせる。

### 7. 「今日読むもの」と選択的な通知 — 優先2・規模: 中

現状: 24時間／7日の件数と記事一覧によるダイジェストがある。表示上限は全体100件・情報源10件。外部通知はない。[ダイジェスト](../backend/src/digest.rs)

提案: 同じ話題を束ね、関心条件・情報源の偏り・新着を考慮した少量の読書キューを作る。選ばれた理由と集計対象期間・表示上限を示す。まずアプリ内で提供し、後に利用者が指定したトピックだけ通知する。通知先・時間帯・上限は明示設定し、既定は外部送信なし。

受入案: ミュート、既読、同一話題、前回紹介済み記事の扱いを固定する。再実行・再起動で同じ通知を重ねず、通知失敗でも記事を既読にしない。Feedlyの重複抑制は参考事例であり、Feederの選定方式は独自提案。

### 8. 必要な記事だけ翻訳・短い要約 — 優先3・規模: 中〜大

現状: Reader用のAI要約・翻訳は未実装。

提案: 詳細画面で要求された記事を対象に、翻訳・短い要約を生成する。結果は原文と分離し、使用した本文の版・範囲・生成日時を表示する。全文がなければ「配信された説明文からの要約」と示し、原文で確認できる表示を用意する。外部検索を行う調査アシスタントにはしない。

実装上の条件: 提供元・モデル・鍵・利用上限は `.env`、鍵はworkerだけに渡す。本文ハッシュ＋モデル＋プロンプト版＋言語でキャッシュする。記事中の指示を命令として扱わず、モデルにネットワーク取得や状態変更の権限を渡さない。要約失敗時も通常の読書経路は動くようにする。

受入案: 原文にない主張、数値・否定の取り違え、短すぎる入力、日本語／英語を固定fixtureで評価。品質・費用・待ち時間を測定してから自動実行範囲を広げる。

## 着手順と評価

1. 収集の継続位置・待機制御をOpenSpec化し、合成テストと実SNS接続の受入を分ける。条件付き取得は既存実装を維持する。
2. 重複索引と記事版保存を追加スキーマとして設計する。原本・既読・スター・順序を保持し、更新前退避と復元検証を受入条件にする。
3. 保存検索の編集UI・条件プレビューを先に整え、トピック表示と読書キューへ発展させる。
4. ニュースレター／外部アダプターは情報源ごとに検証する。AI翻訳・要約とリアルタイム配信は、必要性と運用負荷を測って選ぶ。

効果測定の候補は、取得遅延、未取得ページの解消時間、重複グループの訂正率、読書キューから実際に開いた割合、通知の重複率。まだ測定していないため、改善率や工数日数は示さない。発行日時の信頼性が低いソースは取得遅延の統計から分ける。話題性を測る場合は収集対象・対象期間・取得失敗を必ず併記する。

継続的な動向確認には、今回参照した各社の公式更新履歴、W3C／Bluesky等の仕様、実装対象ソースのAPI変更告知を購読候補にする。公開日・確認日・提供開始／試験中の区別を残し、独自の提案と確認済みの仕様を混ぜない。

今回の作業は公開資料とコードの確認・提案作成のみ。実データ、稼働コンテナ、アプリコード、`.env`、既存のCompose変更は編集していない。
