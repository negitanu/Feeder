## Adopted planning contract
Planning was delegated to Astra. Its delivered initial API/storage/ownership plan in `docs/reader-catchup-plan.md` is adopted. The parent formalizes that plan here so implementation can proceed; implementation agents finalize concrete DDL and Rust helper signatures in their module documents before integration.

## Reader scope
This release completes four linked slices: reliable collection (separate change), revision history, conservative related coverage and a finite human catch-up queue. It reuses existing detail/visit actions. It adds no research workspace, entity graph, page-monitoring renderer, automatic external messages or AI claims about importance. Settings and acknowledgements belong to the existing shared Reader database, not fictional per-person accounts.

## Additive storage and ingest
New module migrations are called only by v10, retaining v9 construction unchanged. Revisions use article_revision_state and article_revisions, grouping uses article_story_index and article_story_exclusions, catch-up uses catchup_preferences and catchup_acknowledgements. State is foreign-keyed to articles/feeds and included in complete database backups. Existing article values and reading state are never reset by the migration. Existing rows are legacy baselines, not newly observed articles; migration does not fabricate past versions.

An accepted collection transaction passes each normalized entry and an ingest kind (initial, normal, recovery) to the revision hook. The hook stores/upserts the article, records snapshots only for substantive title/content/URL changes, updates the current fingerprint and related index atomically. Date-only changes do not generate new content revisions. Source update time and Feeder observation time remain distinct. Freshness excludes initial/recovery backfill from new-event recommendations. History is bounded with truncation and earliest retained history exposed; never claim a complete source edit history.

## Selection
GET /api/catchup validates hours=24|168, limit=10|20 and optional mutually exclusive existing feed_id/folder_id. Capture one UTC upper bound per response. Evaluate at most 5,000 recent eligible candidates (plus one for truncation detection); expose scanned, eligible_count for the evaluated set, truncated and collection_incomplete. A new candidate must be unread, normally ingested and have a valid publication instant in the window and not in the future. An update candidate must have an actual content change after its last recorded visit, within the window. Exclude muted articles and the exact acknowledged revision. Legacy baselines cannot masquerade as new events.

Rank lexicographically by explicit interest-term match, priority feed, actual update, then recent event time and deterministic article ID. No opaque truthfulness/popularity score. Terms are literal case-insensitive title/body matches (maximum 20, 80 Unicode characters each); priority feed IDs maximum 20, validated existing sources. Aggregate conservative related members into one representative without changing underlying state. Use indexed potential matches, then at most 100 related-group expansions; each expansion scans at most 500 candidates per index branch. Any candidate, expansion or related-member bound sets truncated. eligible_count counts representatives in the evaluated portion, not unexamined remainder. Limit displayed representatives to two per source host; source diversity means distribution-host balance, not independent reporting or proof. Expose reason codes and matched values. Fewer than the requested count is valid. Recommendations are computed, not silently marked read.

## API and concurrency
Use the exact endpoint and DTO names in the initial plan. Common Article adds revision, content_fingerprint, changed_at, has_update. GET interests returns a revision; PUT replaces the whole validated configuration with optimistic revision checking. PUT acknowledgement atomically checks current article revision/fingerprint before inserting confirmed/skipped; stale writes return 409. DELETE acknowledgement removes only the supplied event and is idempotent, leaving newer events intact. Article deletion returns 404. Exclusion changes grouping only and can be reversed.

Revisions GET returns snapshots descending with before_revision pagination, default/max 10/20, has_more, next_before_revision, history_complete and history_start. Related GET returns bounded members with reasons; muted entries are omitted. No GET mutates reader or acknowledgement state. All routes inherit existing session/Origin/CSRF checks and bounded request validation. Rendering uses plain text, not source HTML.

## UI
The parent provides URL-backed list/catch-up mode navigation. CatchupPanel owns its period, count and source selector; it does not pretend that hidden ordinary-list filters apply. Shared interests are edited in an initially collapsed section. Every item shows source, absolute time, selection reasons and related count; opening reuses normal article detail. Confirmation and skipping have clear distinct labels and an Undo. Failed or stale saves do not silently discard state. Revisions/related coverage are initially collapsed within article detail. Pending responses cannot overwrite a newer selection. Existing theme tokens, keyboard focus, 390px layouts and reduced-motion behavior are preserved.

## Stages for the eight ideas
This release implements collection, related coverage and revision history, plus the explicit-interest/finite-queue portions of topic discovery and daily reading. Full topic trend statistics, newsletter ingestion, source adapter discovery, external notifications and optional translation/summary remain subsequent work. The reason is staged delivery with verifiable data semantics and no new provider credentials or runtime services in the first release, not a claim that these ideas are implemented.
